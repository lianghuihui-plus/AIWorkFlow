# 技术设计

## 要解决的问题

结合已确认需求和真实代码仓库，设计功能在现有架构中的实现方案。方案聚焦架构与代码组织，足以支撑后续任务拆分，但不展开为逐行编码说明。

## 工作方式

- 先从 `repository_context.root` 调查相关模块、入口、调用链、数据结构和项目约定，不根据需求名称猜文件。
- `code_evidence` 只登记当前仓库真实存在的文件和符号；计划新增或修改的内容写入方案正文，不把计划名称当作现状证据。正常仓库使用 `anchored` 模式；只有配置目录确实为空时才使用 `greenfield` 并填写 `greenfield_reason`。
- 明确功能归属的现有模块，需要新增、修改或复用的文件、类、组件、接口和数据结构。
- 说明各模块、类和组件的职责边界，以及调用、事件、状态和数据如何在它们之间流动。
- 对关键架构选择说明依据与权衡，并覆盖异常、兼容、生命周期和必要的可观测性。
- 可以使用伪代码或必要图表解释复杂逻辑，但不生成正式代码。只要产物包含流程图、类图、关系图、架构图、时序图或状态图，就必须使用以 `mermaid` 标记的 Markdown 围栏代码块绘制；不要求为简单内容机械补图。

技术设计不创建执行任务。任务边界和依赖由任务规格阶段根据批准后的方案统一拆分。

## 最低交付内容

产物必须覆盖现状代码证据、方案目标、模块与文件变化、类或组件职责、主要接口与数据结构、模块交互和关键流程、重要决策与权衡、影响范围和风险。结果清单登记方案覆盖的已确认需求 ID 及可验证的 `code_evidence`。

## 必须停止的情况

代码仓库不可用，或未确认选择会改变模块归属、架构边界、数据所有权、公开兼容承诺或重大成本时，提交阻塞问题。局部且可逆的代码组织选择由 Agent 根据仓库事实决定。
