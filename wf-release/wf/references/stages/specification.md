# 任务规格

## 要解决的问题

把已批准技术方案转换成若干可执行编码任务，并为每个任务形成能够指导实际编码的规格。任务规划和逐任务规格属于同一个业务阶段。

## 任务规划

任务包中 `facts.work_kind=task_planning` 时：

- 结合技术方案和真实代码边界拆分任务，不按文档章节机械拆分。
- 每个任务应有清晰编码目标、相对集中的修改范围，并能在不混入其他任务的情况下完成。
- 依赖只表达前置代码或接口必须先落地的硬依赖，不把偏好的实施顺序写成依赖。
- 每个已确认需求至少由一个任务承接。

任务规划产物解释拆分原则、任务目标、范围和依赖；结果清单登记任务索引，由内核分配稳定 ID。

## 逐任务规格

任务包中 `facts.work_kind=task_specification` 时：

- 只描述当前任务要做什么、为什么这样做、大致怎么做以及完成后达到什么目标。
- 基于 `repository_context.root` 核对相关模块、现有文件、类和接口，不照抄技术方案或猜测代码位置。
- 明确涉及的文件、类、接口、关键行为、实现约束、依赖结果、边界和非目标。
- 保留实现阶段需要自主判断的局部细节，不把规格写成逐行代码清单。

任务规划和逐任务规格都不得设计测试文件、测试用例、Mock、断言或单元测试实现；单元测试由独立测试阶段负责。

## 最低交付内容

任务规划必须覆盖全部已确认需求并形成无循环的硬依赖。单任务规格必须覆盖任务目标、关联方案、前置依赖、预计修改范围、实现思路、关键行为与约束、完成标准和非目标。

## 必须停止的情况

代码仓库不可用，任务无法在既定方案内形成清晰编码边界，或继续会迫使 Agent 改变已批准需求或技术方案时，提交阻塞问题。普通实现细节和可逆技术选择留给实现阶段。
