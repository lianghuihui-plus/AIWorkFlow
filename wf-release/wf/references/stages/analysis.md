# 需求分析

## 要解决的问题

完整阅读 PRD，从混合平台和新旧能力描述中提取目标平台真正需要实施的功能点，为后续代码方案提供准确范围。

## 工作方式

- 以任务包中的 `target_platform` 为过滤基准，不假设整份 PRD 都属于本端。
- 代码调查只用于确认相关模块、入口和能力是否存在，不在本阶段展开调用链、类设计或完整技术方案。
- 区分目标端、包含目标端的跨端协作和纯其他端内容；保留判断理由及 PRD 来源。
- 区分新增能力、修改已有能力和复用已有能力。目标端和跨端的 `modify`、`reuse` 必须以 `repository` 来源登记真实的 `<相对路径>#<符号>`；纯其他端内容只保留 PRD 依据和排除理由，不在目标仓库中寻找其他端证据。已有能力已经完整满足且本端无需改动时明确排除，不把它包装成开发任务。
- 提取本端需要实现的行为、约束、异常和兼容要求；业务背景只保留到能够解释功能点的程度。
- 多份 PRD 冲突、平台归属不明或关键行为无法确定时，先判断是否真的阻塞后续代码设计。

Markdown 自由组织，但应让审核者能快速看清“本端做什么、不做什么、为什么”。结果清单为每个候选功能点登记平台范围、变更类型、范围理由、处理状态和结构化来源；PRD 使用工作空间路径，仓库使用 `<相对路径>#<符号>`，用户决定使用 `D-id`，当前反馈使用 `<W-id>#feedback`，Agent 推断使用 `self`。不要把不同来源写成同一类事实。

## 最低交付内容

产物必须说明目标平台、纳入的本端功能点、排除或延期内容及理由、跨端依赖、关键行为与约束、原始依据，以及仍存在的冲突或合理推断。

## 必须停止的情况

只有平台归属、是否需要本端改动或关键行为的未知答案会改变实施范围，并且无法从 PRD 与现有事实可靠判断时，才提交阻塞问题。可以明确隔离的其他端内容直接排除，不为形式完整而提问。
